我手里在做一套 TCP CUBIC 拥塞窗口的核算服务，想让它成为传输层仿真里可以独立跑起来的一个组件：上游把一次丢包事件之后的关键量交给它，它负责算出任意时刻的拥塞窗口应该是多少、此刻处在 CUBIC 主导还是 TCP 友好主导、以及是否仍在快速收敛阶段。范围就限定在 CUBIC 窗口演进这一件事上，仅经 HTTP 对外提供，不需要抓包、不需要防火墙面板、也不涉及令牌桶限速或排队队长那类东西。

窗口演进的数学内核要立得住。以最近一次丢包时刻为时间原点，丢包前窗口记为一个峰值窗口，窗口大小以 MSS 段数为单位。三条关系必须同时成立：窗口随时间按立方曲线增长，即当前窗口等于一个立方系数乘以「当前时间减去回到峰值所需时间」的三次方再加上峰值窗口；在回到峰值的那个时刻曲线斜率恰为零，也就是窗口先在峰值下方缓慢逼近、越过后再加速超过峰值；回到峰值所需的时间由峰值窗口、乘性缩减因子和立方系数三者共同决定，缩减因子固定取 0.7。给定当前时刻，服务既要给出立方曲线算出的窗口，也要给出一条线性的 TCP 对照窗口，并按标准里的判据决定当前实际采用哪一支：在低带宽时延积的场景下 CUBIC 会退让到 TCP 友好区，用线性对照值；否则走立方值。请把「当前时刻恰好等于回到峰值所需时间时窗口精确等于峰值」这条自洽性守死，不能因为浮点或分支写歪了就在这一点上偏出去。

需要守住的行为不变量要一并落实：只增大峰值窗口，回到峰值所需的时间应当变长、越过峰值后重新超越峰值的时刻也随之推后；把当前时刻取在回到峰值所需时间的正上方，立方窗口应严格大于峰值，取在下方则严格小于峰值；把立方系数加倍，回到峰值所需的时间应当变短；快速收敛阶段的判定要能随「本次峰值相对上一次记录的峰值是升还是降」而正确开合，不能永远返回同一个状态。任何一个基础量不合法都要在开算前挡下并给出可区分的错误：峰值窗口小于等于零、立方系数小于等于零、时间取负、往返时延小于等于零，都属于非法输入，返回带类型的结构化错误而非抛出未捕获异常或返回空值。峰值窗口取零这种退化情形也归为非法而不是算出一个零窗口了事。

除了给定单一时刻的求值，服务还要支持给定一串递增的采样时刻、一次性把整条窗口演进轨迹推出来，每个采样点都带上立方值、线性对照值、最终采用值和当前所处的分支，供上游画曲线或做回归核对；这条轨迹接口和单点求值必须共用同一套窗口函数，不允许出现两套算法各算各的、导致同一时刻两个接口结果对不上。此外要提供一个把当前所有内置标准情形回显出来的只读接口，以及基本的运行状态供监控采集。请随服务预置一个丢包之后窗口先低于峰值、再沿立方曲线爬回并越过峰值的可核对算例，让人一眼能验证曲线方向和峰值点是否对得上。

技术上用 Python 3.12 配 FastAPI 实现，按职责把窗口数学内核、请求校验、HTTP 路由、轨迹推进各自拆成独立模块，避免把全部逻辑塞进一个大文件。提供 Docker 一键构建并启动服务，基础镜像用 python:3.12-slim。附带覆盖上述关键行为的自动化测试：峰值点窗口精确等于峰值、增大峰值使回到峰值时间变长、立方系数加倍使该时间变短、越过与未越过峰值时窗口与峰值的大小关系、TCP 友好分支在低带宽时延积下被正确选中、四类非法输入分别被挡、单点与轨迹两接口同一时刻结果一致、以及并发多请求之间互不串扰。
